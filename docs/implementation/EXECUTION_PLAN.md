# Codex 实施计划

计划版本 1.0，2026-09-13。目标是可复现、可验证的开源 alpha；不以本计划保证完成时间或生产成熟度。任务状态和依赖的唯一机器来源是 [TASKS.json](TASKS.json)。

## 1. 开始前

1. 确认工作目录为主仓库，读取 AGENTS.md 与执行包，查看实际 Git 状态和本地未提交改动。
2. 将 STATUS.md 的已知问题作为待复现基线，而非假定当前代码仍然完全相同。
3. 按 TASKS.json 选择第一个依赖满足的未完成任务。普通实现无需逐项征求同意；不要越过运行环境的权限边界。
4. 建立独立开发环境和测试数据库；先确认地址指向测试实例，再执行迁移和故障注入。不能拿 `.env` 默认连接指向的未知数据库做破坏性测试。
5. 完成一个任务的代码与对应验证后更新状态。发现真正阻碍，记录原因、需要的输入和下一项可独立推进工作。

本包完成不等于 T00-T15 完成。本轮只准备文档的状态必须保留为 todo。

## 2. 五个阶段

| 阶段 | 任务 | 必须得到的结果 |
|---|---|---|
| 产品与契约落地 | T00、T01，及提前的 T05 | 运行基线、可执行 schema、语义与官方 A2A 最小适配已验证 |
| 安全与审计基础 | T02、T03、T04 | 身份可信、请求可信、失败关闭、交付前持久化 |
| 完整交付闭环 | T06、T07、T08、T09、T10 | OPA + Presidio + 输出校验 + 双视图 + A2A 互通 |
| 开发者体验 | T12 | 一套启动方式、轻量客户端、可运行示例与有用错误 |
| 变更、故障与 alpha 证据 | T11、T13、T14、T15 | 兼容性检查、真实依赖故障测试、发布候选证据及真人试用 |

阶段是产品阅读顺序，技术执行以依赖为准。T05 必须提前，T04 不可拖到最后，T11 可在核心版本管理完成后与体验工作并行。T15 无参与者时保持待外部验证，不阻止完成工程候选包。

## 3. 技术路线与代码归属

保留 FastAPI、SQLAlchemy/Alembic、现有路由骨架；明确拆分契约模型、策略适配、内容处理、交付核心、注册版本管理和审计。现有名称可调整，但不要无必要地重写整个仓库。

| 现有位置 | 改造方向 |
|---|---|
| `app/api/agents.py` | 受控注册；组织归属不由公开请求赋权；视图发现与所有者权限 |
| `app/core/security.py`、`app/api/auth.py` | 当前身份/权限验证、token 生命周期、可实际使用的请求签名与验证 |
| `app/core/interceptor.py` | 迁入 OPA adapter；保留兼容接口可选，但不保留第二套放行来源 |
| `app/services/transform.py` | 统一真实执行入口；严格投影、Presidio adapter、完成清单与深拷贝 |
| `app/api/query.py` | 变薄；委托统一交付服务，锁定快照、校验结果、提交记录后返回 |
| `app/models/schemas.py`、`alembic/` | 不可变契约/视图版本、受控身份、delivery receipt、outbox |
| `app/services/audit_writer.py` | 持久化来源从临时队列转为 PG outbox；消费确认、恢复、幂等 |
| `app/api/audit.py` | 所有者/管理员可见范围，默认不返回其他主体日志 |
| `app/api/topics.py` | 第一版仅明确公开通知，执行独立 publish/subscribe scope 与资源限制 |
| `tests/` | 单元、真实依赖集成、官方 SDK 互通、故障与消费效果的可收集测试 |

建议新增 `app/contracts/`、`app/adapters/`、`app/services/delivery.py`、`policies/`、`examples/meeting_views/`。这些是建议归属，不要求机械创建空目录。对外接口先通过 T05 确认，避免暴露与官方类型冲突的字段。

## 4. 任务交付说明

### T00：重建可复现的验证基线

- 记录已有测试数量、收集方式和运行结果，包括默认未被收集的 hacker_agent.py。
- 建议以 Python 3.12 建立新的 `.venv`，前提是与选定的依赖均兼容。旧 venv 不删除、不复用其不可信原生扩展。
- 固定运行/测试依赖，补齐测试依赖清单；记录版本决策。无法安装时说明原因，不能修改预期结果躲过问题。
- 对现有默认拒绝、未知 effect、missing transform、失败跳过、审计错误路径建立针对实际函数/请求入口的回归用例。新安全期望在修复前失败可以记录，不叫基线全绿。
- 构建最小真实 PostgreSQL/Redis 测试设施，后续扩展 OPA/Presidio；迁移只跑测试数据库。

### T01：把有限契约变为可执行校验

- 按 CONTRACT_SPEC.md 实现正式 schema、模型、引用/路径/类型/版本检查，样例全量加载。
- 对规范和契约版本分别验证；拒绝未知字段、非法 effect、空 principal、未知 processor 和不支持 conditions。
- 定义唯一的 AND/OR、deny 优先、不可变视图处理语义及 OPA 决策结构。
- 不构建通用策略编译器，不把旧代码宽松行为写入新标准。

### T02：身份、scope 与可见范围

- 默认受控登记；先支持管理员预置组织/角色，再签发 Agent 凭据。外部请求不能凭 domain 获得组织权限。
- 核验当前 is_active、授权修订及所需 scope；停用后既有 token 不能继续访问。增加独立于契约版本的当前视图/会议资源 grant，角色不变时撤销某视图也立即约束旧契约。
- 审计只允许相关主体或授权管理员访问；视图发现不泄露不可见契约。
- 公开通知仅允许批准事件及可公开资源的元数据 ID/版本，使用严格请求 schema，禁止任意 content/自由文本；不要通过宣传“只发公开内容”保留原来的任意广播旁路。
- 补凭据轮换/撤销的最小管理方式及速率/并发限制，避免公开 bcrypt 路径阻塞事件循环。

### T03：可信上游与请求边界

- 为 Hub 转发提供实际可验证签名；推荐持久化 Hub 签名密钥并使用受控公钥分发，或加密存储目标共享密钥。选择一种，写明密钥存储、轮换和信任建立。
- 签名覆盖实际发送的字节、方法、路径、时间戳和唯一 nonce/request_id；验签能拒绝篡改、过期和窗口内重放。不能只签一个未实际发送的规范化副本。
- 生产回调只允许管理员批准的目标/网络；校验 scheme、解析后的地址、重定向与 DNS 再绑定；阻止 metadata/loopback/未批准内部地址。合法内部 Agent 必须以明确批准规则开放。
- 示例本地回调走隔离开发配置，不弱化生产默认值。应用复用受限连接池，同时设置分段与总超时、并发、响应大小、JSON 深度等边界。

### T04：持久化交付记录与 outbox

- 在 PostgreSQL 中新增 receipt/outbox（或等价的数据库事务方案）；数据返回前提交成功。
- 消费者使用稳定事件 ID、幂等写入、锁或领取租约、有限重试/失败队列与补偿轮询。事务失败后事件不得消失。
- Redis 仅做加速通知；停机、重启、多消费者和重复处理不影响数据库恢复来源。
- 定义 validated/ready_to_send 与客户端真正收到的区别。不要假造 received 状态或 exactly-once 交付保证。
- 普通日志/outbox/审计不存原始 payload、敏感匹配片段或密钥；查询范围沿用 T02。

### T05：提前验证官方 A2A 接口

- 核对并固定官方 SDK 与兼容的协议版本，在本地使用官方客户端/服务端类型跑最小调用。
- 选定项目自己的扩展标识命名空间，声明契约引用/视图和返回结构，不声称已经得到官方扩展认可。
- 记录 Agent Card、能力发现、必需扩展协商、消息/数据部分、错误映射和最小代码样例。
- 将最终接口决定记录在 `docs/implementation/decisions/`，同步契约草案。此处只验证适配形状，完整交付在 T10。

### T06：OPA 决策适配

- 同机/本地服务 REST 接入，固定 Rego 模板读取经过校验的契约数据；接入包不需要用户编写 Rego。
- 输入服务端可信上下文、视图和不可变契约快照；输出验证过的结构化决策。
- 记录策略修订与契约 digest，确认绑定一致；缺失 result、非法类型、目标不一致、超时均失败关闭。
- 单元测试与真实 OPA 测试都覆盖；旧引擎只允许离线对比，不能参与“任一允许就放行”。

### T07：统一字段处理、Presidio 与输出校验

- 实现受限路径的结构投影、源/输出 JSON Schema 校验和单一处理入口；不修改原始输入对象。
- Presidio 仅对保留文本执行基线 en/EMAIL_ADDRESS/[EMAIL]；模型/profile 未就绪时不把服务标为可处理该视图。
- 明确多命中、空字符串、可选字段、未知实体/语言、异常与超时的行为；先测标注样本，再记录召回/误检。
- 严格执行所有 required processor，不支持 processor 不能 no-op。输出记录和黄金样例一致。

### T08：完整查询交付核心

- 将身份/OPA/可信上游/原始校验/投影/检测/输出校验/当前撤权检查/审计提交串成一个入口。
- 同一请求绑定契约、策略、检测配置快照；数据面不出现半升级。最终当前授权检查与 receipt 许可持久化同一事务并发控制，以许可提交为线性化点验证撤权顺序。
- 实际 API 跑通 EX-01..EX-10，并让两个本地消费样例完成分配或待分配任务。限制 query 必填 meeting_id，核验批准资源、提供方绑定和响应 meeting_id 一致性。
- 保留旧 API 时也经过同一核心；无法安全适配的旧 API 默认禁用并写迁移说明。依赖失败不得回退原文。

### T09：版本注册与按权限发现

- draft/validated/active/retired，发布只由所有者/管理员触发，服务器重新验证。
- 已激活版本不可覆盖；请求解析为明确版本，发现只返回当前可见的视图摘要。
- 旧版本、缓存与回滚受当前撤权/停用规则约束；注册引用不能跨所有者访问。

### T10：A2A 与交付核心接通

- 按 T05 的协议映射将 T08 核心接入官方 SDK；不能另写一条绕过安全核心的 A2A 路径。
- 覆盖 Agent Card 发现、正确/缺失扩展、两个视图、拒绝与依赖错误的协议行为。
- REST 与 A2A 使用相同输入时交付 data 和安全决策一致，允许协议信封不同。

### T11：变更检查和旧契约迁移

- 实现有限 schema 差异、视图投影差异与登记消费者样例检查。给出 compatible/breaking/review_required，权限变化单列。
- 不支持的复杂比较返回 review_required，不能默认为 compatible。按 CONTRACT_SPEC.md 的发布表分别控制草案保存、激活和切换默认版本；breaking 不自动切换，review_required 不能激活。
- 生成旧 v0.2 到新草案的离线迁移报告；只有可准确转换的规则生成草案，禁止静默丢弃条件和自动激活。
- 正向兼容升级、不兼容字段删除、类型变化、权限扩大、回滚撤权均验证。

### T12：开发者交付包

- 一个容器方案启动 Hub、PG、Redis、OPA、必需检测服务及合成 Agent，或清楚说明哪些组件内嵌；锁定镜像和依赖版本。
- 轻量 Python client 支持发现视图、请求固定版本、处理稳定错误；无须在应用端重写安全组件。
- 契约检查、样例预览、两个消费示例与复现脚本可独立运行；示例不调用付费模型或写外部系统。
- 首次模型下载/冷启动和稳定运行时间分开报告；不虚构 5 分钟部署保证。

### T13：真实依赖、故障与性能门槛

- 覆盖 ACCEPTANCE.md 的自动场景，特别是重启/重复消费、DB 提交失败、OPA 无决定、Presidio 失败、超大/慢响应、撤权竞态和输出漂移。
- 测试加载真正数据库模块、运行 lifespan 与迁移，不能全用 SQLite/FakeRedis 替代；本地隔离测试不碰生产。
- 测量初次加载与稳定运行、不同 payload/并发的 p50/p95/错误率/内存/审计积压，记录环境和样本量。根据测量形成 alpha 限制，不凭配置声称并发能力。
- CI 分离快速与集成测试，确认全部预期测试可收集；文档变更无需新增镜像实现的测试。

### T14：开源 alpha 候选与文档校准

- 同步旧 README 和产品说明，把未实现或尚未验证的声明删除/标示；引导到新示例和限制。
- 补 LICENSE（以所有者意图和依赖许可核对为基础）、贡献方式、安全报告方式、发布说明、版本与升级策略。
- 整理每个 AC 的证据、已知限制、可复现命令、依赖版本。技术 alpha 通过不代表真人试用或生产成熟。
- 准备本地候选包/变更说明；对外发布、推送和部署按当时用户授权执行，不能由本计划自动授权。

### T15：独立用户试用

- 邀请流程/说明与记录模板可预先准备；未经授权不代用户联系任何人。
- 真实未参与开发的人按 README 完成内外部调用与消费任务；记录耗时、求助次数、业务代码量和卡点。
- 无参与者时使用 awaiting_external_validation，不能以另一个 AI 自测代替。消除试用发现的问题后重跑受影响验收。

## 5. 验收与状态管理

任务状态：todo → in_progress → done，另有 blocked 与 awaiting_external_validation。done 必须包含变更文件、验证命令/环境、结果和相关 AC 的证据位置。依赖未完成不得标记下游 done。

自动验收失败时修复实现并重跑受影响项；不要改松契约或黄金样例来遮掩失败。产品范围确实需调整时，同步 PRODUCT/CONTRACT_SPEC/ACCEPTANCE/任务清单并写设计决定。

从状态中恢复时先验证上一个 done 的证据仍适用于当前代码。T14 的工程候选可完成而 T15 仍待外部验证；用户问进度时必须分别报告。

## 6. 原则与当前不做

- 不做通用 Rego/Python 插件市场、自动谈判、多个 SDK、可视化治理平台、所有文件类型检测和完整身份联邦。
- 不要求每个阶段重新审批；代码实现按明确计划推进。只有实际缺少必要信息/权限时提出具体问题，并继续无依赖工作。
- 任何未知语义优先拒绝，不以“兼容旧版本”为由保留原有不安全路径。
- 所有异常演练使用本地合成数据和隔离服务；不要扫描第三方目标或真实内部网络。
